# MR Review Reply

把本次對話中已完成的審閱結果，整理成給 MR 作者看的留言並發佈。審閱本身不在本 skill 範圍，這裡只負責四件事：確認對象、改寫成對外留言、發佈、回報。

## 為什麼需要這個流程

對話中的審閱結果是寫給使用者看的，裡面會有本機路徑、對使用者的提問、內部推論過程。MR 留言的讀者是作者與其他 reviewer，他們沒看過這段對話。他們需要知道三件事：怎麼審的、結論是什麼、每一項要怎麼處理。作者通常會依編號逐項回覆，所以留言要能獨立閱讀、每項有穩定編號，語氣也要讓人願意接受建議。

## 輸入解析

使用者通常這樣下指令：`use gitlab mcp 將審閱結果回應到 web/game-launcher mr!50`。

- **專案**：`group/project` 形式，也接受 GitLab URL（`.../group/project/-/merge_requests/50`）。沒給時，用 `git remote get-url origin` 推出。
- **MR 編號**：`mr!50`、`!50`、`MR 50`、`#50` 都視為 IID 50。
- **審閱結果**：預設是本次對話中最近一次完成的審閱。使用者指定檔案時改讀該檔。
- **模式**：
  - 預設直接發佈。使用者下這個指令本身就是發文授權。
  - 使用者提到「草稿」「先給我看」「dry run」時，只產出內文給使用者，不發佈。
  - 使用者要求「回覆在上一則底下」時，改為回覆既有 discussion，見「發佈」。

## 發佈前檢查

這些檢查保護的是「對外發出錯誤或過期內容」這件難以收回的事。任何一項不通過就停下來向使用者說明，不發文。

1. **確認有無gitlab mcp工具** 若無gitlab mcp工具，就無法發佈內容回饋，故必須優先檢查。沒有MCP工具時，提示使用者安裝MCP。
2. **確認有審閱結果可發。** 對話中沒有已完成的審閱、也沒指定檔案時，不要邊審邊發。請使用者先審閱，或指出要用哪份結果。
3. **確認專案路徑。** 呼叫 `get_merge_request`，`project_id` 用 `group/project`。
   - 找不到時，比對目前 repo 的 git remote。remote 與使用者寫的路徑只差筆誤時（例如 `play-report-v2` 與 `player-report-v2`），改用 remote 的路徑重查，並在回報中說明修正。
   - 差異不像筆誤時停下來問。
4. **確認 MR 狀態。** `state` 不是 `opened` 時停下來問。對已 merged 或 closed 的 MR 留審閱意見，通常不是使用者的本意。
5. **確認審閱的版本就是 MR 目前的版本。** 比對審閱時的 commit 與 `diff_refs.head_sha`。審閱時的 commit 優先取審閱結果中記錄的 HEAD，沒有記錄時才用本機 `git rev-parse HEAD`。
   - 不一致時停下來，因為行號與結論可能已過期。列出兩個 sha，讓使用者選擇重新審閱，或在留言中明確標註審閱的是舊版本。
6. **讀既有留言。** 呼叫 `get_merge_request_notes`（`sort: desc`），找出：
   - 先前是否有審閱留言，例如同一位使用者、標題含「審閱」「verify」「review」。有的話這次是第 N 輪，記下上一輪的項目編號。
   - 作者是否已逐項回覆，常見格式是「項目／處理／commit」表格。
   - 是否已有內容相同的留言，避免重複發佈。

## 改寫審閱結果

### 保留

- 每項發現的檔案與行號（`path:line`，用 repo 相對路徑）、commit sha、實際執行的指令與結果。
- 原審閱的嚴重度等級，不自行升降級。原本沒分級時，依「會不會造成錯誤行為」分成 WARNING 或 SUGGESTION，並在審閱方式中說明是你分的。
- 事實與推測的區分。沒有實際重現的推論，標註「（推測，未實際重現）」。

### 移除或改寫

- 本機絕對路徑（`/Users/...`）改成 repo 相對路徑。
- 寫給使用者的內容，例如「要我幫你改嗎」「你可以…」，以及對話前後文的指涉，例如「如前所述」「剛才」。
- 內部過程：子代理、工具名稱、agent ID、暫存檔路徑。
- `.env` 值、token、帳密等機密。內網 IP 等環境資訊，只在作者需要時保留。
- `@username`。GitLab 會通知被提到的人。需要提到某人時寫名字不加 `@`，或放進反引號。

### 發佈前重新核對

審閱結果裡的數字（測試數、task 數、requirement 與 scenario 數）與行號，發佈前回到原始檔案或指令輸出重算一次。對話中的報告可能算錯，對外發出後更正的成本高得多。

### 分級與處理方式

每則留言都附「等級說明與處理方式」表，第一輪以外的輪次也一樣。讀者不一定看過上一輪；「0 CRITICAL」也只有在讀者知道 CRITICAL 涵蓋什麼時才有意義。

原審閱有自己的等級定義時沿用它的定義。沒有時，用下列預設定義，每次留言用語一致，讀者才能跨輪比較：

| 等級 | 意義 | 建議採取的方案 |
|---|---|---|
| **CRITICAL**（或 HIGH） | 會造成功能錯誤、安全或資料問題；或 requirement 未實作、task 未完成 | 建議合併前修正 |
| **WARNING**（或 MEDIUM） | 規格或設計與實作不一致、缺少測試證據，或特定情境下可能出錯 | 建議合併前處理；OpenSpec change 則在 archive 前處理。需要延後時，請在 MR 說明理由 |
| **SUGGESTION**（或 LOW） | 可讀性、一致性或邊界防護，不影響現行行為 | 可以順手處理，或另開 follow-up；不處理也不影響合併 |

寫進留言時：

- 列出這套等級的每一級，數量為 0 的也列，「本次項目」欄寫「無」。
- 「本次項目」欄列出這一輪落在該等級的編號，例如 `W1、W2`。
- 「建議採取的方案」寫的是處理時機與方式。每一項具體怎麼改，寫在該項的「建議方案」。
- 個別項目的處理時機與等級預設不同時，例如某個 SUGGESTION 建議 archive 前順手處理，在「建議的處理順序」說明，不要改動表格的定義。

### 編號

每項發現給穩定編號：CRITICAL 用 `C1`、WARNING 用 `W1`、SUGGESTION 用 `S1`。原審閱用其他等級時（例如 HIGH／MEDIUM／LOW），改用 `H1`、`M1`、`L1`。

第二輪起，新項目的編號**接續上一輪**。例如上一輪到 `S4`，這一輪的新建議就是 `S5`。作者常用一張表回覆多輪意見，編號重複會讓人分不清是哪一輪的 `S1`。

### 輪次

- 同一種審閱再做一次才算下一輪，例如同一個 change 的 verify 第二次。標題寫「（第 N 輪）」，並附「上一輪項目追蹤」。
- 種類不同的審閱，例如 verify 之後另做一次單一檔案的 code review，標題改寫「補充」，不標輪次，也不附追蹤表。
- 不論哪一種，編號都接續這位 reviewer 在本 MR 用過的所有編號，避免與任何一則既有留言撞號。

## 留言架構

依下列順序組成。沒有內容的段落整段省略，不要留「無」。完整範例見 `references/example.md`，第一次使用本 skill 或拿不定格式時先讀。

```markdown
## {審閱類型}結果：`{審閱對象}`{（第 N 輪）}

{開場一到兩句：致意，並先講結論}

### 審閱方式
- **範圍**：HEAD `{sha7}`（與本 MR 目前的 head 相同）{；比對的規格或檔案範圍}
- **方法**：{怎麼審的。例如以 Claude Code 執行 `openspec verify`，每一項都回到程式碼查證}
- **實際執行的驗證**：
  - `{指令}`：{實際結果}
- **未涵蓋**：{沒有驗證到的部分與原因}

### 結論
{各等級數量} + 一句整體評估。

### 等級說明與處理方式
| 等級 | 意義 | 建議採取的方案 | 本次項目 |
|---|---|---|---|
| **CRITICAL** | {意義} | {處理時機與方式} | {編號，或「無」} |
| **WARNING** | {意義} | {處理時機與方式} | {編號，或「無」} |
| **SUGGESTION** | {意義} | {處理時機與方式} | {編號，或「無」} |

### 上一輪項目追蹤（第二輪起）
| 項目 | 狀態 | 依據 |
|---|---|---|

### {等級}
**{編號}. {一句話講清楚問題}**
- **問題點**：{現況與 `path:line`}
- **影響**：{會造成什麼結果；沒有可觀察的影響時直接說}
- **建議方案**：{具體做法；有多個方案時先寫建議的那個，並說明理由}

### 待確認事項
{需要作者、後端或維運確認的事}

### 建議的處理順序
{依等級表的處理方式排出先後；個別項目與等級預設不同時在這裡說明}

{結尾一句客氣語}

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

各段的用意：

- **審閱方式**讓作者判斷這份意見的可信度與涵蓋範圍。只列實際執行過的指令，沒跑的寫在「未涵蓋」，不要寫成「已驗證」。
- **結論放前面**，讓只想知道「能不能合併」的人讀完開場與結論就能停。
- **等級說明與處理方式**把「這個等級代表什麼」「該在什麼時機處理」「這次有哪些項目」放在同一張表，作者不用逐項讀完就能排出處理計畫。
- **上一輪項目追蹤**只寫你實際查證過的狀態，依據寫 commit 或 `path:line`。只看作者回覆、沒查程式碼的，狀態寫「作者回覆已處理，未查證」。
- **每項三段式**（問題點、影響、建議方案）讓作者能逐項決定要不要改。影響是說服的主體，不靠加重語氣。

## 語氣

讀者是同事。留言的目的是讓建議被採納，不是證明誰對。

- **開場致意但不浮誇。** 例如「辛苦了，以下整理這次 verify 的結果供參考。」一句就好。
- **對事不對人。** 描述程式的行為（「目前 `x` 為空時會…」），不描述人（「你漏了」「作者沒處理」）。
- **建議用商量的語氣，嚴重度用事實撐。** 用「建議」「可以考慮」「若方便的話」。CRITICAL 仍要清楚寫「建議合併前處理」，理由放在影響裡。
- **肯定要具體，沒有就省略。** 真的有值得一提的地方才寫，而且要具體，例如「惡意 origin 的八種情境都有測試」。不要泛稱「寫得很好」。
- **保留被指正的空間。** 結尾可以寫「若有判讀不對、或我沒掌握到的背景，再麻煩指正，謝謝！」
- 不堆疊客套，不過度道歉。

## 發佈

- **預設**：`create_merge_request_note`，發一則新的頂層留言。
- **回覆既有討論串**：先用 `mr_discussions` 找到 discussion id，再用 `create_merge_request_discussion_note`。
- **針對特定程式行留言（inline）**：只在使用者要求時做。需要 diff 的 `line_code`，不可自行組出。
- **發佈後要修改**：用 `update_merge_request_note` 搭配回傳的 note id，不要另發一則。
- **草稿模式**：把內文寫進 scratchpad 的檔案並貼給使用者，不呼叫任何寫入工具。

## 回報給使用者

發佈後回報：

- 留言連結：`{MR web_url}#note_{note id}`。
- 一句話摘要留言內容，包含結論與各等級項目數。
- 發佈前做過的修正，例如專案路徑筆誤、重算後更正的數字、移除的內容。
- 停下來沒發佈時，說明是哪一項檢查沒通過、需要使用者決定什麼。
