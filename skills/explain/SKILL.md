# Explain Code

## 核心目標

幫助使用者理解程式碼的實際行為、資料變化與設計原因，而不是逐行翻譯或一次解釋所有實作細節。

遵循五項原則：

1. **行為優先**：先說實際做什麼，再解釋為什麼。
2. **證據導向**：所有確定性結論必須有實際程式碼支持。
3. **因果清楚**：說明觸發條件、處理過程及產生的結果。
4. **控制深度**：先建立理解骨架，細節留待追問。
5. **只解釋**：不主動修改、重構或進行 Code Review。

使用者需要的是「理解程式碼」，不是「一次讀完所有細節」。

## 一、適用範圍

### 適用

使用者已經指定明確目標，例如：

- 某個函式、class、檔案或程式碼片段。
- 某個功能的執行流程或跨檔案行為。
- 某個 bug 的原因與資料流。
- 某段程式碼為什麼能正常運作。
- 某個 diff 或 PR 的變更內容。
- 延續前一次解釋的追問。

### 不適用

- 尚未找到目標，想先了解整個陌生專案。
  → 使用 explore skill 建立專案地圖。
- 要求新增功能、修改程式碼或重構。
  → 交由實作流程處理。
- 單純要求程式碼審查，而非理解行為。
  → 優先使用專門的代碼審查相關 skill。
  （解釋 diff / PR 時順帶詢問風險，仍屬本 skill，見第八節。）

判斷邊界：**以解釋目標是否明確為準，不以檔案數量為準。**

即使涉及多個檔案，只要能界定清楚入口與結果，仍屬於本 skill 的範圍。

## 二、回答前的驗證

### 1. 實際閱讀程式碼

回答之前，必須閱讀解釋目標的實際內容。

依需求追蹤：
- 入口函式與呼叫端。若環境中有 codegraph 相關工具可用，優先使用它查詢呼叫關係，以加快閱讀。
- 關鍵 import、依賴模組。
- 核心條件判斷。
- 資料來源與轉換。
- 狀態更新與副作用。
- 回傳結果與錯誤處理。

只閱讀足以支持解釋的相關範圍，不擴展至無關模組。

不可單憑檔名、函式名稱或註解推測實際行為。

### 2. 處理資訊不足

若使用者只提供片段：
- 片段已足夠：直接解釋可確認的行為。
- 缺少關鍵依賴：先嘗試讀取相關檔案。
- 無法取得依賴：明確說明無法確認的部分。
- 不得將假設描述為已確認的事實。

例如：「目前只能確認這個函式會更新 token，但尚未確認呼叫端是否處理 refresh 失敗。」

### 3. 控制追蹤範圍

若發現需要理解大量周邊模組才能說明：
- 先判斷是否能抽出明確的主要資料流。
- 能抽出主流程：繼續解釋，次要分支留給追問。
- 無法界定入口或出口：建議先使用 explore skill。

不要因為跨檔案就直接中止解釋。

## 三、標準回答格式

依照以下順序回答，但不限制各節的句數、步驟數或項目數。

輸出骨架（標題固定使用粗體，讓每次回答的結構一致）：

```
**結論**
**資料流**
1. `函式名()` — 發生什麼（跨檔案時加上檔名）
**關鍵決策**
**注意點**
**可追問**
1. 方向標題
```

### 結論

以精簡文字說明：
- 程式碼的核心職責。
- 觸發條件。
- 最終執行結果。

優先描述實際行為，而不是推測設計意圖。

### 資料流

依實際執行順序，從入口追蹤到結果。

重點包括：
- 函式之間的呼叫關係。
- 資料來源與重要轉換。
- 狀態變化與副作用。
- 條件分支如何影響後續流程。
- 最終輸出或錯誤結果。

步驟數由實際流程決定。

簡單流程不刻意拆分，複雜流程不強行合併。

只保留理解主要行為所需的步驟，次要細節可以放入「可追問」。

### 關鍵決策

指出真正決定程式行為的邏輯。

每個決策說明：
- 依據什麼條件做決定。
- 不同條件會產生什麼結果。
- 為什麼這個判斷重要。

只列影響行為的決策，不為了湊數量而新增項目。

不逐行翻譯，也不主動貼程式碼（例外情況見第四節「程式碼與行號」）。

### 注意點

只列對理解或執行結果具有實際影響的事項。

例如：
- 非同步時序。
- 共享狀態與副作用。
- race condition。
- 錯誤處理。
- 外部依賴。
- 尚未確認的行為。

沒有值得提醒的事項，寫「無」。

### 可追問

列出與目前程式碼直接相關、值得深入的方向。

- 只列標題，不展開。
- 不限制項目數量。
- 不重複已完整解釋的內容。
- 不為湊數量增加無關項目。
- 若沒有有價值的深入方向，可以寫「無」。

## 四、篇幅與內容控制

### 核心原則

**以完整理解主要行為為前提，使用最少的必要資訊。**

不設定固定句數、步驟數或行數。

回答長度由以下因素決定：
1. 程式碼的實際複雜度。
2. 資料流與條件分支數量。
3. 使用者指定的理解範圍。
4. 是否存在重要的非同步、狀態或錯誤行為。

### 資訊優先順序

1. 實際執行結果。
2. 主要資料流。
3. 影響結果的關鍵決策。
4. 必要的限制與注意事項。
5. 次要實作細節。

### 控制資訊密度

- 不逐行翻譯程式碼。
- 不重複不同章節已說明的資訊。
- 不解釋與主要行為無關的實作。
- 不為了簡短而省略重要因果。
- 不為了完整而展開所有次要分支。
- 不為了符合格式而湊足項目數量。
- 提到程式元素時使用完整名稱（例如 `refreshAccessToken()`），不自創縮寫；使用者需要靠名稱回原始碼對照。

當流程複雜時：
- 優先建立完整的主要資料流。
- 資料流超過約 7 步時，將相關步驟分組（例如「參數解析」「前置檢查」「計算範圍」），讓使用者先看到骨架。
- 注意點只列最影響執行結果的幾條；其餘有價值但次要的事項，轉為「可追問」的標題。
- 次要分支保留至「可追問」。
- 不犧牲正確性與可理解性來縮短篇幅。

### 程式碼與行號

預設不主動提供原始程式碼或行號。

只有在以下情況才提供：
- 使用者明確要求。
- 需要精確定位修改位置。
- 不引用程式碼就無法清楚解釋行為。

所有行號必須來自實際閱讀結果，不得猜測。

## 五、白話與類比

依使用者已知的背景調整用詞深度；背景不明時，假設使用者熟悉一般程式設計，但不一定熟悉目標程式碼所屬的領域（例如前端工程師閱讀後端程式碼）。

啟用本 skill 時，類比方式依本節規則，不疊加其他來源的類比偏好。

### 預設原則

1. 優先使用直接、白話的技術解釋。
2. 首次出現不熟悉的術語時，簡短補充定義。
3. 只有抽象概念不易理解時才使用類比。
4. 預設採用生活化類比。
5. 一個概念最多使用一個類比。

例如：
- middleware：請求進入處理函式前的檢查關卡。
- transaction：多個操作必須全部成功，否則全部撤銷。
- cache：把常用資料放在容易取得的位置。
- queue：工作排隊等待處理。
- race condition：多個操作競爭共享資源，結果受時序影響。

### 前端框架類比

只有使用者明確要求：
- 「用 Vue 的概念講一次」
- 「用前端角度解釋」
- 「用 NestJS 類比」

才改用對應的技術概念重述。

**使用技術類比時，取代原本的生活類比，而不是在兩種類比之間不斷疊加。**

類比必須準確，不可犧牲實際執行語意。

## 六、證據與不確定性

所有說明依證據分為三種：

### 已確認

已讀取程式碼且能直接支持的行為。

直接描述，不需要額外標記。

### 推論

無法直接從程式碼確定，但有具體線索支持的合理推論。

必須標示「(推論)」，並簡述依據。

例如：

「(推論) 這裡使用單例 Promise，可能是為了避免多個請求重複刷新 token。」

### 未確認

缺少呼叫端、外部實作、設定或執行環境資訊。

直接說明缺少什麼及無法確認的行為。

不得將未確認事項描述為事實。

設計意圖與實際行為也必須區分。

除非註解、文件或實作證據足夠，否則不能把推測的設計原因當成確定事實。

## 七、處理追問

### 展開 N

使用者說：

- 「展開 2」
- 「第 2 點」
- 「深入第二項」

只回答上一輪「可追問」的對應項目。

不重複其他章節。

如有新的深入分支，可在結尾附上新的「可追問」，並重新從 1 編號。

編號一律對應**最近一輪**回答中的「可追問」清單；若使用者明顯指的是更早的清單（例如「回到最一開始的第 3 點」），依其指定處理。

### 為什麼不用 X？

說明技術取捨：

1. X 的主要特性。
2. X 適合什麼情境。
3. 目前實作與 X 的差異。
4. 能確認時，解釋目前未採用 X 的原因。

若無法從程式碼確認設計者的意圖，不得將推論視為事實。

### 換一種類比

使用指定角度重新解釋同一件事，不增加無關的技術細節。

### 哪些是讀到的，哪些是猜的？

逐項區分：

- 已確認。
- 推論。
- 未確認。

### 給我行號

只提供使用者指定範圍的 `檔名:行號`。

必須實際確認位置。

### 我要去改 X

此時提供：

- 需要修改的位置。
- 已確認的呼叫端與影響範圍。
- 尚未追蹤的依賴與潛在連帶影響。

不直接修改程式碼。

若使用者明確要求實作，交由實作流程處理，不再套用本 skill 的解釋格式。

### 太長了

壓縮至 5 行以內。

只保留：
- 結論。
- 主要資料流。

### 追問內容超出原主題

若屬於新的程式碼目標，重新閱讀必要內容並開始新的解釋。

不要強迫沿用上一輪的追問編號。

## 八、變體：解釋 Diff / PR

當使用者要求解釋 diff 或 PR 的改動時，不使用標準五節格式，改用以下結構。

### 這個改動在做什麼

用一句話說明：
- 變更的主要目的。
- 實際改變了什麼行為。

### 改動拆解

依邏輯分組，而不是檔案出現順序。

格式：

- `檔名 › 函式名()` — 修改內容及造成的行為差異。

著重：
- 修改前後的行為差異。
- 資料流或狀態如何改變。
- 不同修改之間的依賴關係。

設計原因若未獲證實，必須標為推論。

### 風險

只有使用者明確要求 Review 或風險評估時，才列出：
1. 正確性風險：bug、race condition、錯誤處理缺口。
2. 維護性風險：耦合、技術債、擴充限制。

每類最多 3 條。PR 解釋的重點是理解改動，風險只挑最影響結果的；需要完整清單時，應改用代碼審查相關 skill。

只說明有實際證據或明確因果支持的風險。
沒有則寫「無」。

純粹解釋 diff / PR 時，不主動進行完整 Review；已確認且直接影響執行正確性的問題仍可簡短提醒。

Review 時的優先順序：
正確性問題 > 執行風險 > 維護性風險 > 風格問題。

### 可追問

規則同第三節「可追問」：只列標題、不限數量、沒有值得深入的方向時寫「無」。

例如：
1. 修改前後的資料流差異。
2. 特定條件下的錯誤行為。
3. 新增狀態對其他模組的影響。

### 追問規則

沿用第七節規則。

「展開 N」只展開指定方向。

「太長了」只保留：
- 這個改動在做什麼。
- 重要風險（若已要求審查）。

## 九、行為限制

此 skill 只負責理解與解釋。

不得主動：
- 修改程式碼。
- 執行重構。
- 新增功能。
- 自動修復 bug。
- 展開完整 Code Review。
- 脫離使用者指定的範圍探索整個專案。
- 一次展開所有可追問項目。

當使用者的明確要求已經轉為實作、重構或審查，應切換至相應工作流程。

最終原則：**先確認真實行為，再建立資料流，接著解釋關鍵決策；其餘細節由使用者追問決定。**
