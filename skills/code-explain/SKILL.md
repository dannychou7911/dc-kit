# Code Explain

解釋既有程式碼、功能流程或跨檔案行為時，以「理解實際行為、資料變化與因果關係」為核心，不逐行翻譯程式碼。

## 回答結構

依下列順序回答：

1. **結論**
   - 用 1～2 句話說明程式的核心作用、觸發條件與最終結果。
   - 優先描述實際行為，而非設計意圖。

2. **資料流**
   - 依實際執行順序，從入口追蹤到結果。
   - 說明重要的函式呼叫、資料來源、資料轉換、狀態變化與輸出。
   - 跨檔案流程要標示呼叫關係，不把不同檔案當成獨立功能解釋。
   - 可確認時標註 `檔名:行號`；無法確認時不猜測。

3. **關鍵行**
   - 只挑影響程式行為的關鍵邏輯，例如條件分支、提前返回、狀態更新、例外處理。
   - 解釋條件成立與不成立時的行為差異。
   - 必要時才引用最小程式碼片段，不重複資料流已說明的內容。

4. **注意點**
   - 只列影響正確理解或實際執行結果的重要限制，例如非同步時序、副作用、資料共享、錯誤處理。
   - 區分已確認的行為與尚未確認的部分。
   - 沒有值得提醒的事項就寫「無」。

5. **可深入**
   - 最多列 4 個與目前程式碼直接相關、值得進一步理解的方向。
   - 只列標題並編號，不主動展開。
   - 不為了湊數量而新增項目。

## 解釋原則

1. **行為優先**：先說程式實際做什麼，再說可能的設計原因。
2. **因果清楚**：說明重要操作的觸發條件、產生的結果，以及兩者之間的關係。
3. **追蹤範圍**：以使用者詢問的功能為界，閱讀完成解釋所需的相關程式碼，不擴展到無關模組。
4. **證據導向**：結論必須有已讀程式碼支持。未確認的內容標示「(推測)」或「無法確認」，不當成事實。
5. **術語易懂**：只在影響理解時解釋技術術語，首次出現以一句白話補充。
6. **避免重複**：不逐行翻譯、不重貼完整程式碼、不在不同章節重複相同資訊。
7. **不過度延伸**：除非使用者明確要求，不主動做 code review、效能優化、重構或修改程式碼。
8. **控制深度**：優先解釋影響結果的核心邏輯；單純轉接、格式處理或無關實作細節簡述或省略。

## 篇幅限制

1. 第 1～4 節合計原則上不超過 30 行；複雜流程最多 50 行。
2. 不為了符合行數限制而省略理解核心行為所需的資訊。
3. 流程過大時，先解釋主流程，把次要分支列入「可深入」。
4. 使用條列與精簡段落，避免冗長敘述。

## 追問規則

1. 使用者說「展開 N」時，只深入上一輪「可深入」的第 N 項。
2. 不重複前文已解釋的部分。
3. 展開時仍遵守行為優先、證據導向與不過度延伸的原則。
4. 展開的回答可以再附上新的「可深入」清單，編號重新從 1 開始。
